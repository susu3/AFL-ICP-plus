# AFL-ICP 新方法使用说明

本文说明当前代码树的配置、准备、运行、分析和结果导出步骤。它是操作指南，不表示当前版本已经完成 Linux 端到端验收。请只在本人或实验室控制的隔离 Linux 环境中配置目标；不要把生产设备或公共网络地址作为目标。

## 0. 当前实现范围和重要边界

- 首个闭环目标是 Modbus/TCP。目标管理器目前只内置受支持的 libmodbus recipe；也可使用本地已有的可执行文件。给出任意 GitHub URL 并不能自动推导构建方式。
- `aflicp prepare` 会执行准备 DAG，可能调用配置的 LLM、下载指定 Git 仓库、在 Docker 中构建目标，并用用户 C0 对本地目标做代表性交互 dry-run。它不会启动完整 fuzz campaign，但 dry-run 会向配置的本地服务发送协议数据。
- `aflicp run` 才启动实际 fuzz。Fuzz 热路径不调用 LLM。
- Docker 仅隔离种子生成器和目标构建步骤；campaign/replay 会由 AFLNet/harness 在宿主 Linux 上启动目标子进程。对不完全可信的目标，请把整个实验放入一次性、断网且无生产路由的实验 VM/容器中。
- 本工作区是在 macOS 上编写的。引擎 Linux 编译、容器沙箱、目标构建、真实 dry-run、campaign 和 replay 均未在此工作区验收。请先在实验 Linux 环境完成下文的阶段性验收。

## 1. Linux 主机和 Python 环境

建议先使用隔离的 x86-64 Ubuntu Linux 主机。引擎需要 C/LLVM 工具链、Graphviz 开发头文件、libcap；libmodbus recipe 还需要 autoconf/automake/libtool/pkg-config；PDF 文字层不可用时需要 Tesseract。Docker 必须可用。

Ubuntu 示例依赖命令：

```sh
sudo apt-get update
sudo apt-get install -y build-essential clang llvm llvm-dev make graphviz libgraphviz-dev libcap-dev \
  autoconf automake libtool pkg-config git python3 python3-venv tesseract-ocr
```

在仓库根目录创建位于仓库之外的 Python 虚拟环境，避免引擎快照把虚拟环境也复制进去：

```sh
cd /path/to/AFL-ICP-new
python3 -m venv ../.venv-aflicp
source ../.venv-aflicp/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ./harness
```

可选安装 PP-StructureV3：

```sh
python -m pip install -e './harness[layout]'
```

PaddleOCR 还需要本地模型配置才能离线运行；未准备模型时不要启用 `layout_backend: paddle`。默认配置使用 PyMuPDF 原生文字层，识别质量不足时回退至 Tesseract。

确认命令入口：

```sh
aflicp --version
aflicp --help
```

如果在 ARM Linux 上尝试构建，AFLNet Makefile 的 x86 编译检查可能需要 `export AFL_NO_X86=1`。本实现目前没有 ARM Linux 端到端验收记录，正式实验优先使用与目标工具链兼容的 x86-64 Linux。

## 2. 准备 PDF、用户 C0 和配置文件

将协议厂商 PDF 放到实验主机本地目录；将用户一开始提供的 C0 原始种子放入独立目录。种子可递归读取，但必须至少包含一个非空普通文件。不要把生成种子放进这个原始 C0 目录。

从示例配置创建本地配置：

```sh
cd /path/to/AFL-ICP-new
cp harness/config.example.yaml harness/config.yaml
```

编辑 `harness/config.yaml`，至少完成以下配置：

1. `specifications`：填写一份或多份 PDF 的 `id` 和路径；每个 `id` 唯一。
2. `paths.user_seeds`：填写用户原始 C0 目录。`paths.engine_root: ..` 表示仓库根目录；`paths.output_root` 是本次实验输出根目录。
3. `protocol`：首个闭环填写 `MODBUS`。
4. `llm.profiles`：配置 `text`、`vision`、`coding`、`reasoning` 四个 profile。每个 profile 要设置 provider、endpoint、model 和 API key 环境变量名。Vision profile 必须对应支持图片输入的模型；可令四个 profile 使用同一服务，也可以分别使用不同服务。
5. `target`：推荐设置 `recipe: libmodbus`、授权的 HTTPS GitHub 仓库地址和完整 commit SHA；填写本机 Docker build image ID、loopback 地址和实验端口。不要只填浮动分支作为正式实验版本。
6. `seeds.sandbox.image`：填下一步构建得到的种子生成器容器 image ID。
7. `campaign`、`evidence`、`analysis`、`experiment`：按实验计划设置时长、执行超时、每 N 次周期采样、证据上限、重放次数和重复次数。重试次数在 `llm.api.max_retries` 和 `repair.*_max_retries` 中设置。

示例配置中的 PDF、C0、Git commit、模型、endpoint 和 Docker image 均为占位值，必须先替换。YAML 中只能写 API key 的环境变量名，不要写真实 key。

如果已有本地目标可执行文件而不使用 libmodbus recipe，可改用 `target.executable` 和 `target.launch_argv`；确认目标会绑定在所填 loopback/private 地址及端口，并确认目标进程不会连接其他网络。

## 3. 配置 LLM 凭据和 Docker 镜像

按配置中 `api_key_env` 的变量名，在当前 shell 注入 API key。推荐将四个 profile 指向同一个环境变量名，以便只设置一次；例如把配置里的四个 `api_key_env` 都设为 `AFLICP_API_KEY`，然后：

```sh
read -rsp 'LLM API key: ' AFLICP_API_KEY
echo
export AFLICP_API_KEY
```

如果各 profile 使用不同 provider/key，则分别设置对应环境变量。凭据不要提交到版本控制或放进运行日志。`prepare` 需要 LLM；仅运行已经准备好的 campaign 时，通常不需要 LLM key。

从 `harness/` 构建本地种子生成器镜像和 libmodbus 构建镜像：

```sh
cd /path/to/AFL-ICP-new/harness
docker build -f Dockerfile.generator -t aflicp-generator:local .
docker image inspect --format '{{.Id}}' aflicp-generator:local
docker build -f Dockerfile.target-build -t aflicp-target-build:local .
docker image inspect --format '{{.Id}}' aflicp-target-build:local
```

把第一条 `docker image inspect` 输出的 ID 填入 `seeds.sandbox.image`，第二条输出的 ID 填入 `target.build_image`。镜像构建本身可能需要访问软件源；正式离线复现实验应提前准备镜像、固定基础镜像 digest，并记录最终 image ID。harness 不会自动拉取容器镜像。

## 4. 配置预检

回到仓库根目录并激活虚拟环境后运行：

```sh
cd /path/to/AFL-ICP-new
source ../.venv-aflicp/bin/activate
aflicp validate-config --config harness/config.yaml
```

该命令只检查配置、PDF 路径和 C0 目录，不会调用 LLM、下载仓库、构建目标或发送协议数据。它通过不代表 Linux 工具链、Docker 镜像、Git revision 或目标服务已验证。

## 5. 运行准备 DAG（不启动完整 fuzz）

```sh
aflicp prepare --config harness/config.yaml
```

该步骤会按依赖顺序：渲染和保留 PDF 整页截图、读取文字层并按需 OCR、逐页视觉重建、分段/相关性标注、生成并验证 client/server 六份知识文件、生成并构建协议 adapter、生成并在 Docker 沙箱中执行 seed generator、去空/失败/字节完全重复并形成 `-i` corpus、准备目标、最后使用用户 C0 进行 AFLNet dry-run 和 launch barrier 验证。

完成后命令会输出 `run_id` 和 run 目录。请保存 `run_id`，例如：

```sh
RUN_ID='把 prepare 输出的 run_id 填在这里'
```

默认配置的输出目录相对于 `harness/config.yaml` 解析；以命令输出的 `root` 为准。可查看准备状态：

```sh
aflicp status --config harness/config.yaml --run-id "$RUN_ID"
```

准备失败时先检查 `<run_root>/diagnostics.jsonl`、`<run_root>/adapter/`、`<run_root>/target/` 和 `<run_root>/llm_calls/`。不要通过手工改写 `launch-barrier.json` 或标记 artifact 已验证来跳过失败阶段。

## 6. 启动 fuzz campaign

先确认目标属于隔离实验环境，端口未被其他服务占用，`status` 中准备任务均成功，然后运行：

```sh
aflicp run --config harness/config.yaml --run-id "$RUN_ID"
```

此命令根据 `campaign` 配置启动 AFLNet、目标子进程和证据 writer；默认运行到 `campaign.duration_seconds` 到期后停止并排空证据。运行期间可在另一终端检查状态：

```sh
aflicp status --config harness/config.yaml --run-id "$RUN_ID"
```

实际 fuzz 命令、stdout/stderr、目标配置和每个 campaign 的结果保存在 run 目录。AFLNet 原有 crash/hang/queue 目录不由新 recorder 重复创建。不要在目标地址/路由未经确认时运行该命令。

如果操作员中断 campaign，harness 会尝试停止进程并将 campaign 标记为 incomplete。仅在状态确认是 incomplete、目标和工件仍相同的情况下恢复：

```sh
aflicp resume --config harness/config.yaml --run-id "$RUN_ID"
```

恢复会检查 fuzzer/adapter 等身份并继续原输出目录和证据计数；不要删除或手工合并部分 pack/index 文件。

## 7. campaign 完成后的分析

```sh
aflicp analyze --config harness/config.yaml --run-id "$RUN_ID"
```

分析会读取 campaign 证据、选择有限数量交互、在本机启动目标做配置次数的 replay，并调用 reasoning 模型生成/复核带规范引用的候选。只有 replay、来源引用和 reviewer 门禁满足条件的候选才标记为 confirmed；模型结论仍需人工复核。

主要输出：

- `interactions/campaigns/<campaign-id>/`：交互证据 pack、JSONL 索引和 writer 状态。
- `fuzz/<campaign-id>/`：AFLNet 原生 queue、crash/hang 和运行结果。
- `analysis/revisions/vNNN/findings.jsonl`：逐交互候选和复核材料。
- `analysis/report.json`：当前分析摘要。
- `usage/usage.jsonl`：按阶段记录模型调用和可得 token/费用。

当前分析对 AFLNet crash/hang 产物记录路径/hash/大小，不会把文件再拷贝到 findings，也不进行完整 sanitizer 归因。分析输入主要是被采样的正常交互；所以 `analysis complete` 不能解读为已审查所有 crash/hang，也不等同于没有漏洞。

## 8. 重复实验

要按配置重复运行，请先确认 `experiment.repetitions`、campaign 时长及成本预算，然后执行：

```sh
aflicp experiment --config harness/config.yaml
```

该命令会创建一个 run、准备一次共同工件，并自动运行所有配置重复次数的 campaign 与分析；它会启动真实 fuzz，不是只生成计划。完成后输出实验报告路径，其中记录 C0、corpus、adapter、fuzzer、target hash 和 LLM 用量。请把 LLM token/费用与 fuzz 时长分开报告。

## 9. 离线运行和结果导出

`run` 的 fuzzing 热路径不使用 LLM。对已有且完整的 run，在本地文件、目标和必需工件可用时可以尝试：

```sh
aflicp run --config harness/config.yaml --run-id "$RUN_ID" --offline
```

`prepare --offline` 只在所有 PDF/OCR 模型、LLM 缓存、目标源码缓存/本地可执行文件及容器镜像已存在时可完成；缺少必要缓存时应显式失败，不会自动联网补齐。离线模式不禁止与授权的本地实验目标通信。

导出整个 run：

```sh
aflicp export --config harness/config.yaml --run-id "$RUN_ID" \
  --output /path/to/archive/"$RUN_ID".tar.gz
```

导出路径必须在 run 目录之外。归档包含来源 PDF 快照和模型输出，按实验室数据管理要求保护和转移。
